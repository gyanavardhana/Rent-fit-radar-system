Lesson 1 · 10 minutes

The system flow: evidence first, voice last

You already know how to ship a full-stack application. The new skill is deciding exactly where fresh web evidence and voice transformations belong, so Rent Fit Radar stays credible and debuggable.

Win for this lesson
By the end, you can draw the request path and explain why Anakin is not your recommender, why Sarvam is not your database, and why neither secret belongs in the browser.

1. The product loop

The renter supplies preferences: commute anchor, radius, home type, budget, priorities, and language. The application returns ranked localities with a concise explanation, citations, and optional audio.

Read this left to right as a dependency chain. A good explanation cannot compensate for missing evidence; audio cannot compensate for a weak recommendation.

2. Give each layer one job

Browser

Collect preferences, show loading stages, render locality cards/source links, and play returned audio. It never receives provider API keys.

Your server route

Owns orchestration and secrets. It validates input, calls adapters, normalizes outputs, calculates the ranking, and returns one stable response.

Anakin adapter

Retrieves fresh, citable web evidence. Search returns results with url, title, and snippet. Treat its output as evidence to inspect—not as the final recommendation.

Scorer

A pure local function. It applies your stated weights for budget, commute plausibility, chosen amenities, and evidence quality. This is where product policy lives, so it is testable without API calls.

Sarvam adapter

Translates the already-grounded explanation, turns it into audio, and optionally transcribes recorded input. Sarvam makes the product locally accessible; it should not silently invent the evidence basis.

3. The minimal server contract

POST /api/recommendations
input: Preferences
output: { rankedLocalities, explanation, sources, audio?: { url, mimeType } }

This contract is deliberately small. The UI does not learn which search query was used or which Sarvam model produced audio. That complexity belongs behind the server seam.

Important: build the text-and-sources path first. Add translation and audio only after a real Anakin result has reached a visible card.

4. One request, traced

  1. Renter chooses Koramangala, 1BHK, ₹18k–₹25k, and Kannada.
  2. Browser posts those preferences to your server.
  3. Server asks Anakin focused locality questions and receives source results.
  4. Server normalizes evidence and scores the fixed candidate set.
  5. Server builds a source-grounded English summary, asks Sarvam to translate it, then optionally requests TTS.
  6. Browser renders BTM/HSR/Bellandur cards, source links, translated copy, and an audio control.

6. Your next build move

Create the server route with a hard-coded Preferences object and make one Anakin Search request. Log the title, URL, and snippet. Do not build the UI or voice layer until you can see that evidence.
