Voice + live-web cheat sheet

The compressed system model for Rent Fit Radar.

Two jobs, two providers

Anakin answers: “What fresh evidence exists?”
Search produces source-bearing results: titles, URLs, snippets, and relevance. It is retrieval—not the final recommendation.
Sarvam answers: “How does this renter receive the answer?”
Speech-to-text can capture voice input; translation localizes the explanation; text-to-speech makes the answer listenable.

Request path

Browser preferences / recorded audio → POST /api/recommendations → [optional] Sarvam STT → Anakin Search → local scorer → Sarvam translate / TTS → result cards, citations, audio player

Rules that prevent weak demos

  • Evidence comes before prose: score and cite results before phrasing the recommendation.
  • Keep provider keys server-side; the browser calls your route, never Anakin or Sarvam directly.
  • Voice is progressive enhancement: a text result must succeed even if STT/TTS fails.
  • Show uncertainty: “limited live evidence” is more trustworthy than a fabricated claim.
  • For a sprint, use Anakin Search first. Add scraping only when a specific source needs fuller content.

Terms

  • Retrieval: fetching relevant, fresh external evidence.
  • Grounding: constraining a generated claim to retrieved evidence.
  • Normalization: converting provider-specific responses to stable app types.
  • Adapter: replaceable code that speaks to one external provider.
  • Fallback: a useful degraded response when a dependency fails.
